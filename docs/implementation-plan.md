# FridgeChef Systematic Improvement Plan

Status: pending shared-understanding confirmation

## 1. Objective

Prepare FridgeChef for a public Android 1.0 release whose primary outcome is helping an adult user decide what to eat tonight. The daily path should let the user confirm available ingredients, request a recommendation, and choose a dinner within a five-minute product target under documented test conditions. Missing that timing target is recorded and prioritized but is not, by itself, a release blocker.

The product remains a client-only, local-first app with no developer backend and no automatic analytics or crash-reporting SDK. Users who want Recommendations must provide their own Gemini API key, grant AI data consent, download the official BGE-M3 model, and enable at least one recipe source.

## 2. Scope and Product Boundaries

### In scope for Android 1.0

- Android phones in portrait orientation.
- Android 10 or newer, 64-bit ARM, at least 6 GB RAM, and at least 5 GB free storage as the initial supported-device target.
- Chinese product name `是啊！吃什么` and English product name `FridgeChef`; technical identifiers remain `fridgechef` and `com.chishenme.fridgechef`.
- Chinese and English UI with language-independent ingredient identity.
- Light and dark semantic themes using a clean gray-white surface system and natural dark-green accent colors.
- Home, Fridge, Recommendations, and My bottom-level destinations.
- Ingredient entry, Gemini photo recognition, editable confirmation, cooking history, recipe details, Settings, Diagnostic Information, and user-controlled data deletion.
- A rights-cleared Base Recipe Library containing 300–500 quality-reviewed recipes.
- Multiple enabled Official DatasetPacks, multiple enabled Personal Recipe Libraries, signed official model artifacts, and explicitly enabled Unverified DatasetPacks.
- Manual recipe entry and Gemini-assisted YouTube Recipe Draft extraction.
- Google Play distribution in verified regions, excluding mainland China from the 1.0 target market.

### Deferred

- iOS release and iOS-specific UI optimization.
- Mainland China AI-provider and artifact-download support.
- Tablet-specific layouts and landscape acceptance.
- Manual JSON export and import.
- Full-size dataset distribution until ANN/native indexing and target-device benchmarks pass.
- Monetization, advertising, and in-app purchases. Version 1.0 is free and contains none of them.

### Explicitly preserved outside this plan

- `D:\androidCode\ChiShenMeDemo` is not used as the implementation target and remains untouched.
- Existing user work in the dirty Git worktree belongs to the user and must not be discarded, reset, or silently folded into implementation commits.

## 3. Domain and Behavioral Rules

- A Photo Recognition Result is an editable draft. Only a user-saved result becomes a Confirmed Ingredient.
- A Gemini-extracted YouTube result is a Recipe Draft. Only explicit review and save creates a Personal Recipe.
- Dietary Restrictions are hard filters and are never relaxed. Taste Preferences and time preferences may be relaxed only when no result exists, and the UI states what changed.
- Ready to Cook means no missing main ingredient. Almost Ready to Cook means one or two missing main ingredients.
- The first Recommendation view contains no more than three results and does not load more automatically.
- Default criteria are two servings, 30 minutes, and any difficulty; user changes persist.
- Recently cooked recipes are downranked by default, with a strict no-repeat option.
- Enabled sources participate; disabled sources do not. Multiple enabled sources are searched together and deduplicated by stable recipe ID or content fingerprint, never title alone.
- Enabled Official DatasetPacks replace the Base Recipe Library in normal retrieval. The base library is normal only when no official pack is enabled and acts as a clearly explained temporary fallback when official retrieval fails.
- Personal Recipes from enabled libraries share the ranking pool and receive only a small source boost.

## 4. Recommendation Contract

Recommendation Ready requires all of the following:

1. AI data consent is granted.
2. The Gemini API key passes a live test.
3. The official BGE-M3 artifact passes signature, hash, runtime, and test-embedding checks.
4. At least one recipe source is available.

Every new batch uses BGE-M3 Local Retrieval before Gemini. The fixed 1.0 Gemini model is `gemini-3.1-flash-lite`. Changing the model ID requires a new app release and renewed acceptance evidence. English Recommendations are generated by Gemini from candidates that may originate in Chinese-only datasets.

Only explicit Generate, Load More, or Apply New Criteria actions may call Gemini. Screen entry, navigation restoration, refresh, and background work never call Gemini. Automatic retry occurs once only when the client knows the request did not reach the service. Timeouts, quota errors, authentication errors, and schema failures require explicit retry.

An exact Recommendation batch cache is valid for seven days and is keyed by confirmed inputs, criteria, language, prompt version, photo schema version, ranking version, output schema version, and every active source ID and version. English recipe translations are keyed by recipe ID, dataset version, and language. The user can clear both caches.

On Gemini failure, use a valid exact cache first and otherwise show clearly labeled local candidates. On BGE-M3 runtime failure, explain the degraded state and use the Base Recipe Library fallback. Neither fallback is presented as a complete Gemini Recommendation.

## 5. Privacy, Security, and Trust

- Store the Gemini API key through platform-secure storage backed by Android Keystore where supported.
- Prevent screenshots and recent-task previews only on credential entry and reveal screens.
- Never place keys in logs, diagnostics, SQLite, AsyncStorage, Android backup, exports, source control, or CI.
- Keep ordinary local data inside the Android application sandbox without custom whole-database encryption for 1.0.
- Exclude keys, models, DatasetPacks, temporary files, and caches from Android backup. Include the database and non-sensitive settings.
- Do not copy submitted photos into long-term app storage. A visible disclosure on every photo confirmation screen states that an explicit send action sends the photo to Google Gemini.
- Withdrawing AI consent blocks future Gemini calls while retaining existing local output until the user explicitly clears it.
- Verify the official index and official model and DatasetPack manifests with a bundled public key, then verify every declared file with SHA-256.
- Allow key rotation and signature-format versioning before publishing the first production manifest.
- Treat arbitrary-URL packs as data-only Unverified DatasetPacks. Show domain, size, and risk before installation and again before explicit enablement. Never load scripts, native libraries, ONNX models, or dynamic code from them.
- A failed download, extraction, pack, or optional source affects only that operation or source and never clears unrelated local data.

## 6. UI and Accessibility Direction

- Use compact, tool-like information density rather than oversized marketing cards.
- Establish semantic color, spacing, type, radius, elevation, and motion tokens before page-specific styling.
- Support 200 percent font scaling without hidden primary actions or clipped localized text.
- Use at least 48 dp interactive targets, WCAG AA contrast, clear focus and TalkBack labels, and no color-only status communication.
- Validate Chinese and English, light and dark themes, loading, empty, error, disabled, partial, and success states during each slice rather than at the end.
- Preserve React Navigation. Do not migrate to Expo Router during this work.
- The first visual review slice is the design system, bottom navigation, and Home screen using safe static or existing local data.

## 7. Delivery Sequence

### Phase 0: Establish a trusted baseline

Prerequisites:

- The user reviews and commits or otherwise resolves the current pre-existing dirty worktree.
- Confirm the repository is clean without discarding any user changes.
- Create `feat/systematic-improvements` from the approved baseline.
- Capture current typecheck, test, Android build, and device-launch results before feature edits.

Exit criteria:

- The starting commit is named and reproducible.
- Existing failures are documented separately from new regressions.

### Phase 1: UI foundation, navigation, and Home

Deliverables:

- Semantic light/dark design tokens and reusable accessible primitives.
- Four-destination bottom navigation: Home, Fridge, Recommendations, and My.
- Home screen that prioritizes the next action: confirm ingredients or continue to Recommendations.
- Localized Chinese and English copy using the approved product names.
- Loading, empty, error, disabled, and representative populated states.

Exit criteria:

- Android screenshots, runnable-state note, test results, and commit IDs are delivered for user review.
- The user accepts the visual direction before Phase 2 begins.

### Phase 2: Persistence, migration, and credential safety

Deliverables:

- Explicit schema versioning and staged or transactional migrations.
- Fixtures and upgrade tests for every public schema version.
- No silent reset on migration failure; preserve original data and provide retry and redacted diagnostics.
- Secure Gemini key storage and migration from any insecure legacy location.
- Android backup include/exclude rules and credential-screen protection.
- Separate destructive actions for caches, ingredients, history, personal recipes, downloaded packs, model, key, and all user data.

Exit criteria:

- Migration failure tests demonstrate that original data remains readable or recoverable.
- Keys cannot be found in ordinary storage, logs, diagnostics, backup configuration, or captured credential screens.

### Phase 3: Recommendation Ready setup

Deliverables:

- Guided setup: disclosure, live key test, storage/network check, resumable BGE-M3 download, signature/hash verification, test embedding, and source activation.
- Persistent readiness checklist on the Recommendations destination.
- Wi-Fi download without extra confirmation; cellular download with size confirmation.
- Pause, resume, cancellation, process-restart recovery, and disk-space handling.
- RAM/performance warning with an allowed attempt; insufficient storage blocks download.

Exit criteria:

- Setup needs no more than five minutes of active interaction excluding artifact transfer time as a non-blocking product target.
- A cold model load targets 15 seconds or less with visible progress and cancellation; a warm embedding targets two seconds or less.

### Phase 4: Fridge and Gemini photo confirmation

Deliverables:

- Manual ingredient management and Gemini photo selection/capture.
- Persistent Google Gemini disclosure before explicit submission.
- Editable recognition results with confidence treatment and invalid/blurry-photo recovery.
- Separate Save and Save and Find Recipes actions.
- No retained photo copy after the request lifecycle.

Exit criteria:

- Manual fixed evaluation set of at least 100 photos achieves at least 90 percent precision and 80 percent recall.
- Low-confidence, invalid, blurry, Chinese, and English scenarios remain editable and never auto-save.

### Phase 5: Core recommendation journey

Deliverables:

- Versioned query, prompt, schema, ranking, and cache contracts.
- Unified multi-source retrieval and stable deduplication.
- Three-result Ready to Cook and Almost Ready to Cook presentation with time, difficulty, matched ingredients, missing ingredients, and source.
- Explicit next batch and criteria adjustment; no automatic infinite loading.
- Hard dietary filtering, transparent soft relaxation, recent-history downranking, and strict no-repeat option.
- Seven-day exact-batch cache, translation cache, and clearly labeled failure fallbacks.

Exit criteria:

- At least 100 fixed Chinese and English scenarios achieve a suitable recipe in the top three at least 80 percent of the time.
- Dietary violations are zero; Ready to Cook misses zero main ingredients; Almost Ready to Cook misses no more than two.
- Known recipe time does not exceed the active maximum unless the UI explicitly reports a relaxed time criterion.
- Gemini never changes stable recipe identity.
- The daily core journey has a measured five-minute target. Misses are recorded but do not independently block release.

### Phase 6: Recipe sources and personal recipes

Deliverables:

- A rights and quality audit for the 300–500 recipe Base Recipe Library.
- Signed, resumable Lite and Medium Official DatasetPacks with multiple mirrors and update retention until verification succeeds.
- Resource limits based on total vectors, bytes, and measured query time rather than a fixed pack count.
- Explicit enable/disable semantics for every official, unverified, and personal library.
- Atomic index and cache updates for personal recipe create, edit, delete, enable, disable, and language changes.
- Manual entry and user-reviewed Gemini YouTube Recipe Draft workflow.

Exit criteria:

- The Unverified DatasetPack security suite rejects traversal, limits, hash, ID, JSON, cancellation, interruption, and disk-space failures without changing installed data or enabled state.
- At least 20 fixed public YouTube cooking videos produce structurally complete editable drafts at least 80 percent of the time; no result auto-saves.
- Disabled or deleted personal recipes never appear in a newly generated batch.

### Phase 7: History, My, Settings, and diagnostics

Deliverables:

- History and recently cooked controls.
- Personal libraries, DatasetPack management, Settings, privacy policy, AI consent withdrawal, cache controls, and destructive data controls under My.
- Copyable Diagnostic Information and a reviewed handoff to the public GitHub support repository.
- Diagnostics contain app version, Android version, architecture, memory class, free storage, model version and test state, source IDs and versions with check state, and last error code and time.
- Diagnostics exclude key, photo, ingredient, restriction, personal-recipe, and AI request/response content.

Exit criteria:

- Every destructive action affects only its named data category and Clear All requires explicit confirmation.
- Optional feature failures do not block unrelated core features.

### Phase 8: CI, release hardening, and distribution

Deliverables:

- GitHub Actions checks for formatting, TypeScript, unit tests, and integration tests on pull requests.
- Separate Android release build workflow; local Gradle remains authoritative and EAS remains a backup path.
- Mock and contract Gemini tests in CI. Real Gemini, photo, translation, and YouTube evaluations run manually before release with model ID, prompt/schema versions, date, and results recorded.
- Internal testing, closed testing, and 10 percent, 50 percent, and 100 percent production stages with at least seven days at each production stage.
- Google Play App Signing, offline upload-key backups, verified supported-country list, privacy-policy URL, release notes, Data Safety answers, and public support repository.

Exit criteria:

- No P0 or P1 defect remains.
- No unresolved crash/ANR, data-corruption, key-exposure, dietary-filter, artifact-installation, or core Recommendation blocker remains.
- Google Play vitals and user-initiated reports meet the documented gate for each rollout stage.

## 8. Test Matrix

| Area | Automated on PR | Manual before release | Blocking rule |
| --- | --- | --- | --- |
| TypeScript and formatting | Full | No | Must pass |
| Domain algorithms and migrations | Unit tests | Recovery spot check | Must pass |
| Repositories, caches, and setup state | Integration tests | Device recovery flows | Must pass |
| Dataset and model trust | Security and contract tests | Real mirror/download tests | Must pass |
| Navigation and core screens | Component/integration where practical | Android device walkthrough | Must pass |
| Accessibility and localization | Static/component checks where practical | TalkBack, 200% font, zh/en, light/dark | Must pass |
| Recommendation quality | Deterministic retrieval tests | 100+ fixed scenarios with real Gemini | Thresholds apply |
| Photo recognition | Mock contract only | 100+ fixed photos with real Gemini | Precision/recall thresholds apply |
| YouTube extraction | Mock contract only | 20+ fixed public videos with real Gemini | 80% complete-draft threshold applies |
| Five-minute user journey | No | Timed closed-test observation | Record and prioritize; not independently blocking |

Real Gemini credentials are never stored in GitHub Actions. Manual AI evaluations are explicit cost-bearing release activities.

## 9. Git and Review Protocol

- Use one independently verifiable logical change per commit.
- Use fully English Conventional Commit-style messages.
- Before each implementation commit, run the relevant focused tests, `npm run check`, and `npm run test:types`; run the full test suite for core changes. Record any verification that is genuinely blocked.
- Do not amend, rebase, squash, or rewrite an already delivered UI review commit. Apply requested visual changes in a new commit.
- Do not mix the user's pre-existing worktree changes into a scoped implementation commit.
- Do not start the next major UI slice until the current slice is reviewed.
- Each UI review delivers Android screenshots, runnable-state notes, a Chinese summary, test results, and commit IDs.
- New ideas enter the backlog unless they address security, data loss, or a blocker in the current core path.

## 10. Release and Support Policy

- Release only in regions where Google Play installation, Gemini API behavior, and every primary and fallback artifact path have been verified.
- Mainland China is not a 1.0 target region.
- Version 1.0 is free, with no ads and no in-app purchases. Users remain responsible for Gemini API and network-provider charges.
- Support only the latest production version while preserving migrations from every public version.
- Use a separate public support repository containing the privacy policy, FAQ, known issues, Issue templates, and release notes; publish the privacy policy through GitHub Pages.
- Do not set a product-specific closed-test participant minimum for 1.0 beyond the Google Play requirement in effect at release time. Scenario and device coverage still apply.
- Target adults and do not identify children as a target audience.

## 11. Known Starting Gaps

The current repository already contains substantial uncommitted restructuring and security work. It also currently exposes only three Node test files, has no visible GitHub Actions workflow, and declares a light-only UI style in `app.json`. These are observations, not permission to modify or discard the worktree. Phase 0 must establish the exact approved baseline before the plan is implemented.

## 12. Authorization Gate

This document records the proposed shared understanding. Creating it does not authorize implementation. Business-code, UI, build, dependency, test, and configuration changes begin only after the user explicitly confirms the shared understanding and the pre-existing dirty worktree has been committed or otherwise resolved by the user.
